# VisibilityLab: web application

VisibilityLab is a local web front end for the research pipeline in [`../pipeline`](../pipeline). It
registers samples and their provenance, collects evidence files, runs the existing pipeline in a
separate worker, and shows and exports the sealed per-sample results.

> VisibilityLab is a **report processor**. It never executes, unpacks, decrypts or downloads a
> sample, never launches a sandbox, and never serves a stored binary back. Synthetic fixtures are
> used only by the explicit "Load synthetic demo" action and are never substituted for a missing stage.

## Components

```
browser ──► Next.js frontend (webapp/frontend, 127.0.0.1:3000)
               │  fetch / XHR (CORS limited to localhost:3000)
               ▼
           FastAPI API (webapp/backend/api.py, 127.0.0.1:8000)  ── records requests only
               │  SQLite (WAL) + content-addressed files under VL_DATA_DIR
               ▼
           Worker process (webapp/backend/worker.py)
               ├─ optional: pinned capa subprocess (Stage A/B on PE, Stage C on a CAPE report)
               └─ pipeline.run.run_batch(...)  ← the unchanged research pipeline
```

| Module | Role |
|--------|------|
| `config.py` | settings from `VL_*` environment variables (see [`.env.example`](.env.example)); unsafe switches default to off |
| `db.py` | SQLite schema with **versioned migrations** (`schema_migrations` table; append-only list `MIGRATIONS`) |
| `storage.py` | generated, content-addressed file names; raw evidence (`evidence/`) is kept apart from quarantined PE files (`quarantine/`) and derived results (`jobs/`); path-traversal checks |
| `validation.py` | bounded PE header parser, per-kind JSON schema checks, `.zip` bundle reader (flat, known names only, nothing extracted to disk) |
| `capa_runner.py` | pinned capa: absolute path, version check, argument list (no shell), minimal env, timeout, output cap, isolation acknowledgement required for PE input |
| `services.py` | rules shared by API, worker and demo import (Gate 3, duplicates, supersession, V2/V5 checks on payload upload) |
| `worker.py` | claims jobs, resolves stages, runs `pipeline.run.run_batch`, records everything |
| `api.py` | typed FastAPI endpoints |

### How the web app uses the pipeline

The worker does not reimplement any formula. For each job it:

1. copies the sample's current evidence files (`A`, `B_recovery`, `B`, `C`, `S`, `evidence`) from
   the immutable evidence store into `jobs/<id>/inputs/`;
2. writes a one-sample `specs.json` with the **SHA-256 values recorded at upload time**, so that
   the pipeline's hash gate also detects any change to stored evidence;
3. calls `pipeline.run.run_batch(specs, mapping, jobs/<id>/results)`. This runs the recovery gate
   (`pipeline.recovery`), N1–N7 (`pipeline.normalize`), the measures (`pipeline.metrics`),
   classification (`pipeline.classify`) and the manifest seal (`pipeline.manifest`);
4. renders `report.html` with `pipeline.report.write_sample_report`, verifies the seal with
   `pipeline.manifest.verify_manifest`, and stores statuses, hashes, tool and mapping versions and
   evidence references in SQLite.

Synthetic samples run in pipeline mode `synthetic` against the fictional `fixtures/attack_map.csv`.
Empirical samples run in mode `pilot` with their approval reference, against the official
**ATT&CK Enterprise v20.0** table in [`../mappings/`](../mappings). That table was generated by
`tools/build_attack_map.py` from MITRE's STIX bundle (upstream SHA-256 recorded in
`attack_enterprise_v20.0.provenance.json`).

## Demo mode (no prerequisites)

**New Analysis → Demo mode** creates a *synthetic* sample with a generated fictional SHA-256. It
needs no sample, source record, reports or approval. The sample page then offers a **demo evidence
kit**: the six synthetic inputs (`A`, `B_recovery`, `B`, `C`, `S`, `evidence`) from
`pipeline/synthetic.py`, in the scenario *accepted* (the guide's worked example) or *rejected* (V4
fails, budget 25 > 20). Attach them individually or all at once, or download them and use the normal
upload boxes (same validation), then run the analysis. Demo files are marked `"synthetic": true`, so
empirical samples refuse them. The kit is refused (403) for empirical samples. See
[docs/EMPIRICAL_ONBOARDING.md](../docs/EMPIRICAL_ONBOARDING.md) for the step from demo mode to a
documented benign UPX control.

Empirical mode is unchanged in what it requires (SHA-256, source, date, approval reference) and now
also refuses placeholder approval values such as "n/a", "tbd", "demo" or "test". The app cannot
verify that a reference is genuine; it only rejects obvious stand-ins.

## Two empirical workflows

**1. Analyze existing evidence (fully operational, no tools needed).** Register the sample by its
SHA-256 (with an approval reference), then import capa JSON for A and B, the recovery record, capa
dynamic JSON for C (or a genuine CAPE report, see below), the sandbox labels S and an evidence file,
either one by one or as a `.zip` bundle. Run the analysis.

**2. Local static analysis (needs configuration on an isolated VM).** Upload the packed PE. It is
hashed, its headers are parsed, and it is stored quarantined. If `VL_STATIC_ANALYSIS_ENABLED=true`,
`VL_CAPA_PATH` and `VL_CAPA_EXPECTED_VERSION` are set and `VL_ISOLATION_ACK` holds the exact
acknowledgement phrase, the worker runs capa on it for Stage A. It does the same on a recovered
payload PE for Stage B, but only after the recovery record passes the gate and the payload hash
matches `payload_sha256` in that record. A genuine CAPE report runs through `capa -f cape` for
Stage C, and its own `ttps` labels become S.

Without a required tool or report, a stage is shown as **awaiting input** and its measures are
**n/d**. Nothing is simulated.

Stage statuses: `queued`, `running`, `complete`, `failed`, `not_recovered` (the recovery gate
rejected the record) and `awaiting_input`.

## Setup (Windows, PowerShell, from the project root `review2_pipeline`)

```powershell
python -m pip install -r requirements-webapp.txt
cd webapp\frontend; npm install; cd ..\..
```

## Launch (three terminals in VS Code, all started from `review2_pipeline`)

```powershell
# Terminal 1: API on http://127.0.0.1:8000  (OpenAPI docs at /docs)
python -m webapp.backend

# Terminal 2: worker (must run as its own process)
python -m webapp.backend.worker

# Terminal 3: frontend on http://127.0.0.1:3000
cd webapp\frontend; npm run dev
```

You can also start all three windows with
`powershell -ExecutionPolicy Bypass -File scripts\dev.ps1`. To configure a setting, set it in the
terminal before starting **both** the API and the worker, for example `$env:VL_MAX_PE_MB = "30"`.

Interrupted jobs: when the worker starts, it marks any job left `running` as `interrupted`, and
the job can then be resubmitted. Only one active job per sample is allowed (a duplicate submission
returns 409).

## Synthetic end-to-end workflow (demonstration only)

This walkthrough uses only the bundled **fictional** fixtures. It shows that the plumbing works and
is **not** evidence about real malware behaviour.

1. Start the API, the worker and the frontend (see above), then open http://127.0.0.1:3000.
2. On **Overview**, click **Load synthetic demo**. This registers SYNTH-001 and SYNTH-002 as
   *synthetic* samples and queues one analysis for each.
3. Under **Samples → SYNTH-001 → Analyses → #1**, the stages A, B, C and S are complete, with
   QA 0.75 (3 / 4), VA 0.4 (2 / 5), VB 0.4, DB 0.0, IB 0.6, G 1, L 0, M 2, O 2, S∩C 1, and residual
   classes P=1, K=1 (P+K=2), U=1.
4. Analysis #2 (SYNTH-002): B is **not recovered** (budget exceeded (25 > 20); V4 not passed),
   VA = 0.4, and every B-dependent measure is n/d.
5. Use **Verify seal**, **Printable report** (which carries a SYNTHETIC RUN banner),
   **Evidence / Audit** and **Exports**.

The same check without a browser:

```powershell
python -m pytest webapp/backend/tests/test_workflows.py -k synthetic_demo -q
```

## Security notes

* Binds to 127.0.0.1. A non-loopback `VL_HOST` is refused unless `VL_ALLOW_REMOTE=true`. There is
  no authentication, so do not expose the service.
* Uploads are untrusted. They are streamed to a temp file with a size cap and hashed, then the JSON
  is schema-checked or the PE header is parsed with bounds checks. Request bodies above the largest
  limit are refused before parsing. Original filenames are kept only as sanitized metadata.
* PE files are stored as `quarantine/<sha256>.sample`, read-only and without an executable
  extension, outside any web-served directory, and are never returned by the API.
* capa runs only from an explicitly configured absolute path, at the pinned version, with an
  argument list (no shell), a closed stdin, a minimal environment, a timeout and an output cap. capa
  analyses files statically and does not execute them. Even so, PE analysis is enabled only when the
  operator states, through `VL_ISOLATION_ACK`, that the worker runs in an isolated analysis VM, as
  the proposal requires.
* Dynamic analysis (CAPE) is never run by VisibilityLab. Produce CAPE reports in your own isolated
  sandbox and import them. A report is accepted only if `target.file.sha256` equals the sample.
* Errors returned to the client contain no stack traces. Unexpected errors return an `error_id` that
  is logged on the server.
* No secrets are used or stored. `.env` files and `webapp/data/` are git-ignored.

## Assumptions to confirm

* The CAPE report fields `target.file.sha256` and `ttps` (`[{"ttps": [...]}]` or `[{"ttp": "T…"}]`)
  follow CAPEv2. Check them against your CAPE version.
* The capa command line `capa -j -f pe|cape [-r rules] <file>` and the JSON shape
  (`rules → meta → attack → id`, `meta.sample.sha256`) need checking against the pinned capa release.
* The recovery-record schema (see `pipeline/recovery.py`) must be what the operator's validated
  tool writes.
